# Задание 4. Проектирование продажи ОСАГО

## Принятые решения

Для оформления ОСАГО добавлен отдельный сервис `osago-aggregator`.

Сервис отвечает за:
- отправку заявок ОСАГО во все доступные страховые компании;
- периодический опрос предложений по созданным заявкам;
- сохранение промежуточных статусов;
- передачу предложений в `core-app` по мере получения ответов.

## Хранилище osago-aggregator

`osago-aggregator` имеет собственную БД `osago-aggregator-db`.

БД нужна, потому что:
- сервис работает в нескольких экземплярах;
- обработка заявки занимает до 60 секунд;
- нужно хранить состояние заявки и ответы по каждой страховой компании;
- результат может быть обработан другим экземпляром сервиса;
- требуется избежать потери промежуточных результатов.

## Интеграция core-app и osago-aggregator

Для взаимодействия выбран асинхронный request-reply через очередь сообщений.

`core-app` отправляет команду на расчет ОСАГО в очередь.
`osago-aggregator` получает команду, создает заявки в страховых компаниях и опрашивает предложения.
По мере получения предложений сервис отправляет результаты обратно в `core-app`.

Такой подход выбран, потому что ожидание ответа может занимать до 60 секунд, а синхронное ожидание при пиковой нагрузке приведёт к большому количеству открытых соединений.

### Почему я выбрала Kafka
Для интеграции core-app и osago-aggregator используется существующий Kafka.

Из описания теоритической части для команд точка-точка чаще подходят очереди, например Artemis/RabbitMQ. Но в текущей архитектуре уже используется Kafka как единый брокер событий, поэтому для снижения сложности и отказа от второго брокера использую Kafka.

Интеграция реализуется через отдельные топики:
- osago-quote-requests — команды на расчет ОСАГО;
- osago-offer-events — события о полученных предложениях;
- osago-quote-completed-events — событие завершения расчета или истечения 60 секунд.

## API Web и core-app

Для создания заявки используется REST API, например, POST /api/osago/applications

Для получения предложений по мере поступления используется Server-Sent Events, например, GET /api/osago/applications/{applicationId}/offers/stream

Это позволяет отображать предложения пользователю сразу после получения ответа от конкретной страховой компании.

## Паттерны отказоустойчивости

На схеме применены:

- Rate Limiting — на входе в core-app и при вызовах страховых компаний.
- Timeout — для ограничения ожидания ответа, максимум 60 секунд.
- Retry — для кратковременных сетевых ошибок.
- Circuit Breaker — для изоляции недоступных страховых компаний.

## Масштабирование

Решение учитывает, что сервисы запущены в нескольких экземплярах.
Состояние заявки хранится во внешней БД, поэтому обработка не зависит от конкретного pod.
Очередь сообщений распределяет команды между экземплярами `osago-aggregator`.
