# Задание 3. Анализ проблем и рисков при переходе к росту нагрузки

## Контекст

В текущей архитектуре сервисы `core-app` и `ins-comp-settlement` получают данные о продуктах и тарифах через REST API сервиса `ins-product-aggregator`.

`ins-product-aggregator` при синхронном запросе обращается к API страховых компаний, агрегирует ответы и возвращает единый список продуктов и тарифов.

Сейчас подключено 5 страховых компаний. В ближайшее время планируется подключить еще 5, то есть количество внешних интеграций увеличится в 2 раза.

## Проблемы текущей архитектуры

### 1. Синхронная зависимость от внешних API страховых компаний

`core-app` и `ins-comp-settlement` зависят от скорости ответа `ins-product-aggregator`, а `ins-product-aggregator` зависит от скорости ответа страховых компаний.

Если одна или несколько страховых компаний отвечают медленно, возникает задержка всего синхронного запроса.

Риск:
- увеличение времени ответа;
- тайм-ауты;
- нестабильность пользовательских и внутренних операций;
- ухудшение SLA для партнеров.

### 2. Рост количества страховых компаний увеличивает задержки

Сейчас `ins-product-aggregator` обращается к 5 страховым компаниям. После подключения еще 5 компаний количество внешних вызовов увеличится до 10.

Риск:
- увеличится суммарное время агрегации;
- увеличится вероятность ошибки хотя бы в одной внешней интеграции;
- повысится нагрузка на `ins-product-aggregator`.

### 3. Периодический polling создает лишнюю нагрузку

`core-app` запрашивает данные о продуктах раз в 15 минут, а `ins-comp-settlement` — раз в сутки.

Такой подход неэффективен:
- если данные не изменились, запросы все равно выполняются;
- если данные изменились сразу после запроса, локальная реплика будет устаревшей до следующего запуска;
- при росте количества сервисов-потребителей количество polling-запросов будет расти.

### 4. Возможна устаревшая локальная реплика продуктов и тарифов

Так как данные обновляются по расписанию, `core-app` и `ins-comp-settlement` могут работать с устаревшей информацией.

Риск:
- клиент увидит неактуальный тариф;
- заявка может быть оформлена по устаревшим условиям;
- взаиморасчеты со страховыми компаниями могут быть сформированы на неполных или неактуальных данных.

### 5. Сервис `ins-comp-settlement` синхронно зависит от `core-app`

`ins-comp-settlement` раз в сутки обращается к `core-app` по REST API, чтобы получить все оформленные за день страховки.

Риск:
- если `core-app` недоступен ночью, взаиморасчеты не будут сформированы;
- если данных много, запрос может быть тяжелым;
- нагрузка отчетного сценария влияет на основной сервис оформления страховок.

### 6. Недостаточная отказоустойчивость

При сбоях внешних API страховых компаний ошибки распространяются внутрь системы через синхронные цепочки вызовов.

Риск:
- отказ внешней страховой компании может повлиять на работу внутренних сервисов;
- пользователи и партнеры могут получать ошибки из-за проблем во внешней системе;
- сервисы сложнее масштабировать независимо.

### 7. Сложность масштабирования

При синхронном взаимодействии рост нагрузки на один сервис приводит к росту нагрузки на зависимые сервисы.

Риск:
- придется масштабировать сразу несколько компонентов;
- увеличится стоимость инфраструктуры;
- отдельные медленные внешние интеграции будут ограничивать производительность всей системы.

## Предлагаемое решение

Предлагается перейти к Event-Driven архитектуре для обмена данными о продуктах, тарифах и оформленных страховках.

Для этого добавляется брокер событий Kafka.

### Потоки событий

1. `product-catalog-events`

Поставщик:
- `ins-product-aggregator`

Потребители:
- `core-app`
- `ins-comp-settlement`

События:
- `product_catalog_updated`
- `product_tariff_updated`

Назначение:
- обновление локальных реплик продуктов и тарифов в сервисах-потребителях.

2. `insurance-policy-events`

Поставщик:
- `core-app`

Потребитель:
- `ins-comp-settlement`

События:
- `insurance_policy_created`
- `insurance_policy_updated`
- `insurance_policy_cancelled`

Назначение:
- передача данных об оформленных страховках в сервис взаиморасчетов без ежедневного REST-запроса в `core-app`.

## Использование Transactional Outbox

Для сервиса `core-app` необходимо использовать паттерн Transactional Outbox.

Причина:
- при оформлении страховки сервис должен сохранить данные в свою БД и опубликовать событие `insurance_policy_created`;
- если запись в БД прошла успешно, а публикация события в Kafka завершилась ошибкой, `ins-comp-settlement` не узнает о новой страховке;
- outbox позволяет сохранить событие в той же транзакции, что и бизнес-данные, а затем отдельный publisher гарантированно отправит событие в Kafka.

Также Transactional Outbox можно применить в `ins-product-aggregator`, если агрегатор сохраняет актуальный каталог продуктов и тарифов в свою БД перед публикацией событий.

## Дополнительные требования к обработке событий

### Идемпотентность

Потребители должны обрабатывать события идемпотентно, так как брокеры часто гарантируют доставку по модели at-least-once. Это значит, что одно событие может быть доставлено больше одного раза.

Каждое событие должно содержать уникальный `event_id`. Потребитель должен хранить обработанные `event_id` и игнорировать дубли.

### Порядок событий

Для событий по одной сущности нужно использовать ключ партиционирования:
- для продуктов — `product_id`;
- для тарифов — `tariff_id`;
- для страховок — `policy_id`.

Так события одной сущности будут попадать в одну партицию и обрабатываться в правильном порядке.

### Мониторинг

Нужно добавить мониторинг:
- lag consumer group;
- количество ошибок обработки событий;
- количество событий в DLQ;
- время публикации события;
- время обновления локальных реплик;
- доступность Kafka;
- ошибки интеграции со страховыми компаниями.

## Ожидаемый эффект

Переход на Event-Driven архитектуру позволит:

- снизить связанность между сервисами;
- убрать регулярный polling;
- уменьшить влияние ошибок внешних API страховых компаний;
- ускорить работу `core-app` и `ins-comp-settlement`;
- повысить отказоустойчивость;
- масштабировать потребителей событий независимо;
- обеспечить более актуальные локальные реплики данных.
