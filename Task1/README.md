# Task1. Технологическая архитектура InsureTech to-be

## Цель

Спроектировать технологическую архитектуру InsureTech с учетом требований:

- доступность 99,9%;
- RTO 45 минут;
- RPO 15 минут;
- работа 24/7;
- поддержка пользователей из разных часовых поясов;
- одинаковое время загрузки страниц из разных регионов;
- готовность к росту нагрузки после рекламной кампании.

## Основные архитектурные решения

### 1. Failover-стратегия

Используется:

- Active-Active;
- георезервирование;
д- ве активные площадки.

Обе площадки одновременно обслуживают пользователей.

При отказе одной площадки GSLB автоматически исключает ее из балансировки по health check и направляет трафик во вторую площадку.

### 2. Kubernetes

Используются:

- два независимых Kubernetes-кластера;
- Cluster A в Zone A;
- Cluster B в Zone B.

Выбраны независимые кластеры, т.к. они уменьшают зависимость от сетевой связанности между площадками и снижают риск каскадных отказов.

### 3. Масштабирование

Основная стратегия масштабирования - горизонтальная.

HPA масштабирует количество pod-реплик сервисов по CPU, memory и кастомным метрикам, например RPS.
Все backend-сервисы развернуты как Deployment + HPA.

### 4. CDN

CDN используется для доставки статического контента пользователям из разных регионов.
Это снижает зависимость времени загрузки страниц от географического положения пользователя.

### 5. Балансировка

Трафик проходит по цепочке:

Client → CDN → GSLB → Regional Load Balancer → Ingress / API Gateway → Kubernetes Services.

Для всех ключевых компонентов настроены health checks.

### 6. Rate Limiting

Для B2B API используется Rate Limiting на уровне API Gateway / Ingress.

Лимит задается по идентификатору партнера или API key.
Базовый лимит — 20 RPS на партнера.
При превышении лимита возвращается HTTP 429 Too Many Requests.

Это защищает систему от ситуации, когда один партнер потребляет все ресурсы приложения.

### 7. База данных 
Используется PostgreSQL Patroni Cluster.

В состав входят:

- PostgreSQL Primary;
- PostgreSQL Replica;
- etcd;
- HAProxy;
- pgBackRest.

### 8. Репликация и backup

Используются:
- streaming replication;
- WAL archive;
- резервное копирование через pgBackRest.

Основная цель - это RPO ≤ 15 минут и быстрое восстановление после сбоя.

### 9. Мониторинг

Используются:
- Prometheus;
- Grafana;
- Alerting.

Мониторятся:
- RPS;
- response time;
- error rate;
- CPU;
- memory;
- replication lag;
- health check площадок;
- состояние Kubernetes;
- состояние PostgreSQL.

### 10. Шардирование

Шардирование БД не применяется.

Текущий объем данных — 50 GB.
Для такого объема достаточно PostgreSQL HA, индексов, репликации, backup и оптимизации запросов.
